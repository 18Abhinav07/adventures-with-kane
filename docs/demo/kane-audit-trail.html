How to read the overrides

Why "failed" isn't always "broken"

Five tasks show a human-reviewed override in the log above. Every one of them followed the same discipline, visible in the rationale text: re-run in isolation, get kane-cli's own bug-triage verdict (confirmed / family / confidence), and only then decide. In four of five cases, triage traced the failure to Kane's own automation — a missing hover step in the authored test, a redundant re-verification step oscillating after the real action already succeeded, a stale replay baseline invalidated by a legitimate popover-placement fix. Those get corroborated with a fresh, direct re-run before being marked verified. The fifth — T7's alert sweep — was different: no override needed, because the fix was applied and the sweep passed clean on the next attempt. That's the one case in this build where the gate caught something real and the loop worked exactly as designed: deny → fix → re-verify → pass.
